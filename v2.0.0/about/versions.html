Versions and stability#

This site documents version 2.0.0. Published versions are listed on PyPI. What each one changed is in the changelog.

What a version number says#

HydroModPy follows Semantic Versioning. A pre-release adds a suffix that PEP 440 defines: a for alpha, b for beta and rc for release candidate, then a number, as in 2.0.0rc1.

The rules below hold from 2.0.0 on, and this page is their only statement. The goal is that the 2 line can grow for years without a version 3, so a change that a user can absorb never needs a major version.

Frozen for the whole 2 line#

A run you stored stays readable. Its folder layout, its Parquet and Zarr schemas, its manifest and its provenance can be read by every later 2.x, and so can the keys of its frozen config.toml. Only a major version can change this. A stored format can gain a new version inside the line, and the build that writes it then also reads the older ones.

A calibration session you stored stays readable too. Its session.json, its phases, its trials.jsonl and its trial series are read and shown by every later 2.x, and the run it promoted is a stored run like any other. Resuming a session, running one more of its phases or promoting one of its trials again by replay needs the version that wrote it, because the session records the code that scored its trials. A later version refuses it with a sentence that says so.

The index .hmp/index.duckdb is outside this promise, because it is derived from the run folders. hmp catalog reindex rebuilds it at any time.

Can change in a minor version, with a migration#

This covers the name or the place of a TOML key, an hmp command or flag, a name of hydromodpy.__all__ and the shape of a config table.

The old name of a TOML key or table keeps working until the next major version when the change comes after 2.0.0, so a file written for 2.0.0 loads in every later 2.x. A key renamed in 2.3 still loads in 2.4, 2.9 and every other 2.x, and can only go in 3.0. Inside the 2 line a stable key moves to the key that replaces it and is never removed, and the register of changes refuses a row that would remove one. An experimental key follows its own rule, below. While an old name works it prints a warning that gives the old name and the new one, once per key and per file. hmp doctor --fix-config <file> rewrites your file and the files it inherits, and keeps your comments. The changelog lists the rename under Changed with both names.

A key or a table that only a pre-release wrote (an alpha, a beta or a release candidate) is refused from 2.0.0. The message names every such key the file holds, at once. HydroModPy does not rewrite the file. The list of key changes shows each such key with the version that refuses it and the name that replaces it. A run stored by a pre-release is refused the same way. The keys are listed in hydromodpy/config/prerelease_forms.txt, and the list leaves in 2.2.0. One key is not on it. A pre-release wrote type in [[simulation.process]]. So a project it made still loads with a warning, and hmp doctor --fix-config writes kind.

Each move of a key is one row of the register of changes, hydromodpy/schema/changes.toml, that the loader, the doctor and the generated list of changes all read. A key that moves in a stored document, such as a sidecar or a field store, has its row there too.

An old name of Python, or an old hmp command or flag, follows the rule of two minor versions when the change comes in 2.2.0 or later. It prints a FutureWarning with both names and then does what the new one does. A name, a command or a flag that left before 2.0.0 or in it has no alias. It is refused, with a message that names its new form, until 2.2.

In 2.0.0 the top level became the fifteen verbs of hydromodpy.project.api and their five objects. hmp.read, hmp.index and hmp.Catalog stay beside them, because the runs of a pre-release are read through them. hmp.figure, hmp.report, hmp.calibration_phases, hmp.compare_pair, hmp.example_add, hmp.example_list, hmp.example_show, hmp.Workspace and seven exceptions of results and project are refused with the call that replaces them, such as hmp.show(ref, what='figure', name=...) for hmp.figure. The reading commands that left the command line (the reading actions of catalog, then viz, report, config check, project show and project status) are refused the same way, with hmp ls, hmp show, hmp diff or hmp check. hydromodpy/cli/conventions.py lists them.

Numbers#

A fix that changes the numbers of a run (a head, a flow, a score) is allowed in a minor version and in a patch when the old number was wrong. A scientific correction does not wait. The changelog lists it under Numbers with the size of the change, and it gets a row in the register of changes, hydromodpy/schema/changes.toml. A fix has a bug row with the versions that carry it and the quantities it touches. A rule that changes a number without a bug has a recipe row. The Numbers section of the changelog is generated from these rows, so it cannot forget one. A run stored with an older version keeps its numbers and its version stamp and is never rewritten. Run.label() then calls it exploratory and names the bug.

Defaults#

A file that does not say which defaults it wants follows the defaults of 2.0, for the whole 2 line. So a key you did not write never changes your numbers. The day a default has to move, the edition key comes with it, and only a file that writes the new edition gets the new value. The key is a root key of the file. It is "2.0" when the file does not write it, and config.resolved.toml writes it with every other default. A file that names an edition this version does not know is refused, with the list of the editions it knows. Each default that moves is a default row of the register of changes, and the page of each key in the parameter reference lists its default by edition.

There is one edition, "2.0", and hmp project new writes edition = "2.0" in the project file it creates. A later minor version may add one, with the rows of the register that say which defaults move.

What makes two runs the same#

Two runs are the same computation when they ask for the same thing and the same code and tools compute it. A run asks for its configuration as a file writes it, the bytes and the state of every input file it reads, and the edition of its defaults. A URL counts by its pinned sha256 and a file by its bytes, so the address or the path of an input does not count. What computes is the code of the layers that change a number, the mesh engine with its version, the sha256 of each solver binary and the versions of the numeric packages. [workspace], [workflow], simulation.name, every deliver_to key, the name of the run and its sim_id are not part of the identity.

A release that only touches figures, commands or this documentation keeps that identity, so an identical run is not computed again, and an edit of a solver changes it. A configuration counts by what it writes: a key written at its default value is another identity than no key, because a validator can tell the two apart, and it costs one more computation at worst. A calibration is not part of the identity of the run it promotes, whose file holds its own solve.

A run or a calibration session stored by a pre-release carries an identity made another way. The first time this version meets the same request, it computes it once more, and the new run carries the new identity. Its numbers are the same.

What a sealed run keeps, and how a replay is classed#

A run seals config.toml, what it was given, overrides included, and config.resolved.toml, the same with every default written. The seal also gives the digest of the values it computed, one per field, per column of a quantity and per array of the final state, taken in double precision before a field is rounded for storage. hmp replay <run> plays the run again from those bytes and classes what it compared: bit when every value hashes the same, deviation otherwise, with the size of each difference and the changes of this register it crossed. A source of a pre-release is classed on its stored values, and a copy that carries no values has no class. A moved default or another solver binary goes in the lineage of the replay and refuses nothing, and an input whose digest differs is still refused. --strict refuses a deviation: the attempt ends failed, its fields stay readable, and no seal is written. hmp run <run>/config.toml --frozen is refused with a sentence that names hmp replay. hmp catalog rerun records the keys that moved in the lineage of the new run.

Experimental#

Anything marked experimental may change in any minor version, without the delay above. A file that writes an old key of [calibration] is refused with the new name, and hmp doctor --fix-config rewrites it.

  • In a TOML file: the whole [calibration] section, the VI and TS runtimes of Boussinesq with their settings, partition_release_depth_m, transport.modflow6prt, the MODPATH block, the HFB barriers, the parameters of the soil reservoir beyond its budget, geographic.domain_extent and the custom backend. The parameter reference marks each key. A run lists the experimental keys its file writes in one line of its log, and hmp check shows them.

  • On the command line: the result of hmp calibrate --format json, with the report it reads.

  • In Python: the shape of CalibrationReport, and the solver, solver.extractor and calibration.evaluator plugin ports, as the contracts page details.

  • The sidecars of validity_frame.

Patch#

A patch fixes bugs. It adds no public name, and it asks nothing of you. It can still change a number that was wrong, under the rule above.

What the rules cover#

The names are the ones the generated pages list: the Python reference, the command line reference with its exit codes and what a program reads, and the parameter reference. A module path outside hydromodpy.__all__ is internal, except the short list on the contracts page. So is any HMP_* variable that its generated page does not give to users.

Pre-releases#

A pre-release makes none of these promises.

Stage

Example

What to expect

Alpha

2.0.0a1

Public testing. Keys, API and storage can still change.

Beta

2.0.0b1

Feature complete. The contract changes only to fix a blocker.

Release candidate

2.0.0rc1

Only blocking fixes land.

Final

2.0.0

The version to recommend to users.

Install a version#

pip skips pre-releases unless you pass --pre. To pin an exact release so a project reads the same keys tomorrow, such as 2.0.0 now:

pip install hydromodpy=={{ release }}

A project written for version 1 stays on the tag v1.0.0 of the repository. Version 1 is frozen on the v1.0 branch. It gets no new work.
