Packages#

One row per sub-package of hydromodpy. The summary is the first paragraph of its README.md, the map of the package.

Package

Layer

Modules

Lines

Summary

calibration

yes

92

33 917

Fitting model parameters to observations. A [calibration] table names the parameters to vary, the outputs to compare, the criterion that scores them and the search method. The package turns that table into a search. An optimizer proposes parameter values, one trial runs the model with them, the outputs are scored against the observations, and the session is written to disk as it goes.

catchment

yes

90

19 920

The catchment layer takes a DEM and an outlet and gives the catchment, its river network and the ground the model sits on. It conditions the DEM and routes flow on it through a terrain engine, which is a port (terrain/, with its own README). It delineates the catchment, cuts the domain polygons and extracts the streams. It also holds the surfaces of the domain, the routing of water on the cells of the model top, the stream-network criterion on arrays and the French departments used to pick data tiles. The package is a layer because the mesh, the model, the solvers and the results all start from the same ground and the same network, and it knows no solver and no data provider. The DEM arrives as a resolved dem_path with its digest and state, and a geology map is read by a function the caller passes as an argument.

cli

yes

74

11 550

The command line, with the hmp and hydromodpy entry points. It parses arguments, calls the code that does the work, formats the output and turns an exception into a typed exit code. It holds no scientific logic, so a result that the command line gives is the one that hydromodpy.project.api gives. Fourteen of the fifteen verbs have a command, and open has none. Under their names status is ls --disk, compare is diff and trash is catalog trash. The families workspace, project, campaign, data, site, config and privacy, and catalog apart from trash, call the lower packages directly because no verb covers them.

config

yes

13

6 841

The root of the configuration. HydroModPyConfig is the one Pydantic model that aggregates every section of a project TOML file, and anything a user can write in a project file must load through it and round-trip. The package is thin on purpose. Each section model lives next to the code it configures, and this package is the only place where the section types of the other packages are imported together. Every other layer refers to its own section model, never to the root.

core

yes

127

23 753

The kernel leaf of HydroModPy. Every other package may read core, and core reads no sibling package, not even under TYPE_CHECKING. It holds what several layers need and none should own: the base of every config model, units, the paths of a project and a workspace, run state, the I/O primitives, the typed exceptions and a few kernels that two layers must compute the same way, such as the sign of a budget flux and the digest of a block of values.

data

yes

172

29 582

Everything a run reads from outside is here: provider APIs, the files of the user, their cache and the typed records handed to the layers above. Each [data.<name>] section of a project TOML is one variable, and VARIABLE_SPECS in loading/_dispatch.py is the one list of them. A variable owns its cache and the unit of its records and leaves the provider to a class of the DataSource port (source/, with its own README), so adding a provider touches no variable. The data folder is the cache, each fetched file has a JSON sidecar beside it, and there is no database. The package is a layer because the loaders, the workflow and the calibration need data in one typed form, and none of them should know which provider or file it came from.

display

yes

53

12 815

display draws. It takes a run that is already computed, or data that is already loaded, and writes PNG figures, HTML pages and the tables behind them. It never runs a solver and never writes into the storage of a run. It reads only core and results, and everything it reads from a run goes through subject.py.

mesh

yes

75

16 451

This package turns a project into the cells that MODFLOW 6 and the other solvers compute on. It reads the catchment, the rivers, the lakes and the geology, returns one PlanarCellMesh that the rest of HydroModPy reads, and writes and reads the mesh in the usual exchange formats, so a mesh opens in ParaView or gmsh. It reads core, schema and catchment, and it also carries the mesh port, because its registry sits at the root of the package.

model

yes

96

23 066

The model is what a groundwater solver reads, written without any solver. A [domain] table says where the aquifer lies, a [flow] table gives its parameters, initial heads, boundaries and sinks and sources, and a [transport] table holds the tracking settings. The package turns those tables into typed config models and the config models into runtime objects. It puts the forcings on the cells of a mesh, maps the properties onto those cells, binds loaded data to the flow and holds the arithmetic of the daily soil reservoir that turns the weather into recharge. Flow (flow.py) is the object the setup binds loaded data to, Model (model.py) is the frozen object a solver reads, and prepare_solver builds it from the Flow. The same step gives it the top and the bottom of every cell, by the rule the backend declares in domain/cell_column.py, so no solver samples the DEM itself. The package is a layer because the solvers, the workflow, the calibration and the results all need one description of the model, and none of them should own it.

project

yes

57

20 365

The public face of HydroModPy. api.py holds the fifteen verbs that hydromodpy and hmp expose: open, run, check, calibrate, spinup, replay, stop, status, trash, compare, show, export, publish, example and doctor. A verb takes text, numbers, paths and mappings and gives back a value with to_dict, a path or diagnostics, so a server sends what it gets. A reference is a path, a name read in workspace, or the object itself, and nothing is looked for above the working directory. kept_readers.py keeps read, index and Catalog at the top level beside the verbs.

results

yes

180

51 102

What a run leaves on disk and how it is read back. A run directory holds Zarr 3 arrays and Parquet 2.6 tables, sealed by the manifest.json that the run writes last. The DuckDB index .hmp/index.duckdb is derived from the run and session directories, so disk is the truth and hmp catalog reindex rebuilds the index at no cost.

schema

yes

25

5 494

The shapes that HydroModPy writes for a reader outside this process. One family is for a front end, the JSON Schema of the whole configuration and the sentence of each code that a check gives. The other is for an orchestrator, the job directory that a capability writes and the declaration of each capability. The package reads core and itself, so a document can be described without importing any science.

solver

yes

200

49 100

The numerical backends. solver.backend names the flow backend, the table [solver.<name>] holds its settings, and a [[simulation.process]] entry names the solvers each process runs. The package holds the adapters that turn a built Flow or Transport into a backend run, the extractors that read the backend’s files into the results store, and the registry that pairs a <process_type>_<name> key with each. Four flow backends ship, MODFLOW 6, MODFLOW-NWT, Boussinesq and the linear reservoir, with the transport tools that go with them.

workflow

yes

45

11 715

The order in which a project is built and run. A file such as project.toml becomes thirteen steps, from validation to the seal of the run. Each step takes an immutable PipelineState, does its part and returns the next one. A Pipeline chains the steps, records them in the journal of the run and can resume a run from the artifacts of the steps already done. The Project facade and every workflow launcher, simulation or calibration, call these steps, so one file always drives one lifecycle.
