The grammar of a HydroModPy file#

One TOML file describes a run. Its sections are listed in TOML parameters; this page gives the rules they all share: tables, inheritance, quantities, dates, paths, free keys and profiles. The rules are written by hand. Every key this page cites and every TOML block it shows is checked against the models of the code.

Tables and arrays of tables#

A section is a TOML table: [flow]. A table can sit inside another one: the header [flow.param.K.field] opens the table field of the table K of param. You do not need to write [flow] first.

A request that you may repeat is an array of tables, written with double brackets. Each [[export]] block is one export, in the order of the file. The same form holds the sources of a data variable, the processes of a simulation, the observation points, the stages of a calibration and its objective blocks.

1[[simulation.process]]
2id = "flow_main"
3type = "flow"
4solvers = ["modflow6"]
5
6[flow.param.K.field]
7kind = "homogeneous"
8unit = "m/s"
9value = 5e-5
10
11[[export]]
12variables = "watershed"
13
14[[export]]
15variables = ["watertable_depth", "seepage_mask"]
16time = "last"

Three rules hold for the whole file.

  • A file has at most 24 top-level sections. A name that is not one of them is refused: Unknown top-level TOML section(s): flows.

  • A key that the table does not know is refused, and the message names the table: Unknown TOML key(s) in [flow]: flow_regme.

  • Three sections are required in every file: [workflow] with workflow.mode, [workspace] with workspace.project_root, and [geographic]. project_root = "." means the folder of the file. In its standard mode, [geographic] needs [geographic.catchment] with geographic.catchment.catch_def, and catch_def = "dem" needs geographic.catchment.dem_init_path. With these four keys, hmp config check accepts the file.

base_config: start from another file#

A file can inherit every table of another one. It writes only what changes.

a child file, five lines · keys link to their card
1base_config = "base.toml"
2
3[simulation]
4name = "nancon_daily"
5
6[simulation.time]
7step_value = "1 day"

base_config is a top-level key, so it goes before the first table header. Its value is a path, read from the folder of the file that holds it. An absolute path works, and ~ is expanded. The parent can have its own base_config: the chain is read from the oldest ancestor down, and a loop stops with Detected circular base_config chain. Once the files are merged, base_config is gone, and the merged result is what the schema validates.

hmp run adds two more layers on top of the chain, in this order: files given with --overlay, then values given with --set. Environment variables named HMP_SET_* come last.

hmp run run.toml --overlay daily.toml
hmp run run.toml --set simulation.name=my_run
HMP_SET_SIMULATION__NAME=my_run hmp run run.toml

A --set value is read as TOML when it can be, and as a plain string otherwise: 200 is a number and my_run is a string. In an environment variable name, two underscores stand for a dot.

Merging: tables, lists, __append, __merge, __delete#

The same merge applies to the files of the chain, to overlays and to --set values.

The child writes

The result holds

a number, a string, a boolean

a list of values, figures = [...]

the child’s list, which replaces the parent’s

figures__append = [...]

the parent’s list, then the child’s items

key__delete = true

the parent’s key or table removed, with all that is under it

[[x]] blocks

the child’s blocks, which replace the parent’s, whatever their number

[[x__append]]

the parent’s blocks, then the child’s

[[x__merge]] blocks, as many as the parent’s

the blocks merged one by one, in order; another number is refused

Inside one table, the merge runs in three passes: the deletions, then the keys the file writes, then the appends. A key that is deleted and written again in the same table starts from nothing: this is why sources__delete = true, followed by a new list of sources, does not inherit the old keys. key__delete needs the literal true, key__append needs a list, and key__merge needs an inherited list of tables of the same length and is refused next to the plain key. To see the file a chain resolves to, before validation, run hmp config resolve <file>.

five rules in one file · keys link to their card
1base_config = "base.toml"
2
3[flow.param.K.field]
4value = 1e-4                    # kind and unit are inherited
5
6[display]
7figures__append = ["duration_curve"]
8
9[[export__append]]
10variables = "watershed_dem"
11
12[data.hydrography]
13sources__delete = true          # drop the inherited list
14
15[[data.hydrography.sources]]
16source = "bdtopage"

Two traps come from inheritance, not from the merge itself.

  • A list that other keys depend on. In [flow], every table of param must be named in flow.param_list. A child that adds [flow.param.Ss.field] and does not touch the inherited list is refused: flow.param contains ids not declared in flow.param_list: Ss. Write param_list__append = ["Ss"]. Or leave param_list out of every file: it is then taken from the tables.

  • A table that changes shape. value belongs to kind = "homogeneous", and values to "heterogeneous". A child that switches the kind must remove the old key with value__delete = true, or the file is refused with Extra inputs are not permitted.

An empty string is not a value: a key written "" is dropped when the file is read, as if it were absent, and the default of the model applies.

Quantities and units#

Many fields take a length, a duration or a rate. The form of a field says how: number or "<n> m" reads a bare number, or a string made of a number, a space and a unit. Write the string in quotes: snap_dist = "150 m". Unquoted, 150 m is not valid TOML.

The registry counts 87 fields typed as a quantity. They come in five kinds. In each, a bare number is in the unit shown, and a string needs a unit: "150" is refused.

For a volumetric flow, write m^3/s or m³/s. The shorthand m3/s, which the form of the field shows, is refused today.

The value of a flow parameter, flow.param.K.field.value, works another way. Its unit sits in the sibling key flow.param.K.field.unit, or inside the string: unit = "m/day" with value = 4.3, or value = "4.3 m/day" alone. Both at once are accepted when they agree, and refused when they differ. Left out, the unit is the SI one of the name: m/s for K, - for Sy, m-1 for Ss, and - for any other name. The accepted units are -, m/s, m/day, m/h, cm/s, cm/day, cm/h, mm/s, mm/day, mm/h, m-1 and cm-1. The validated file keeps the value as written, with its unit. It is converted to SI when the parameter is built: 0.36 in m/h becomes 1e-4 in m/s.

quantities, validated on step 1 · keys link to their card
1[geographic.catchment]
2snap_dist = "150 m"
3buff_area = "10%"
4
5[domain.depth_model]
6thickness = "30.0 m"
7
8[flow.param.K.field]
9unit__delete = true
10value = "4.3 m/day"

Three more cases. geographic.catchment.buff_area is the only field that reads a percentage: "10%" enlarges the catchment area by 10 %, "500 m" or "2 km" is a distance, and a bare number keeps an older rule that the field warns about. Some keys carry the unit in a sibling key, as in flow.sinks_sources.lakes.<name>.bedleak_unit. And a field that takes a list of values takes one value too: variables = "budget" and variables = ["head", "budget"] are both read by export.variables.

Dates and durations#

The simulated window is simulation.time.start_datetime and simulation.time.end_datetime, with a step. Both dates are required once the table exists. The end date is inclusive: end_datetime = "2002-12-31" ends the run at the end of that day. The window must end on a step boundary, and the run refuses it otherwise: a monthly step cannot end on the 15th.

three years at a monthly step: 36 stress periods · keys link to their card
1[simulation.time]
2start_datetime = "2000-01-01"
3end_datetime = "2002-12-31"
4step_value = "1 month"

simulation.time.step_value is a positive whole number with a unit among hour, day, month and year: "1 month", "1 day", "6 hour". A bare number needs step_unit beside it. A unit that disagrees with step_unit is refused, and so is "1 week".

Write dates as quoted strings, "2002-10-15". A TOML date without quotes is read by some fields and refused by others: simulation.time.start_datetime accepts it, and the date_start of the data tables does not.

An instant is a date, "first" or "last". A date selects the stress period that holds it, so the same date names the same month on a monthly or a daily run. The key export.time also takes a list of instants.

A window has two spellings. A two-item list, ["2001-01-01", "2002-12-31"], is the form of export.period and of the scoring_window of a figure. A table with start and end is the form of calibration.scoring_window. The data tables take a date_start and a date_end; left out, they use the simulated window.

instants and windows, validated on step 4 · keys link to their card
1[display]
2time = "2002-10-15"
3
4[display.overrides.hydrograph_log_nse]
5scoring_window = ["2001-01-01", "2002-12-31"]
6
7[[export__append]]
8variables = "discharge"
9period = ["2001-01-01", "2002-12-31"]
10
11[[export__append]]
12variables = "watertable_depth"
13time = "last"

Paths#

A path in a file is read from the folder of the file you run, the last one of the chain. It is not read from the folder of the parent that wrote it. A parent in shared/base.toml that writes dem_init_path = "dem.tif" is read in the folder of the child that inherits it, work/child.toml: the loader merges the files first, then resolves the paths. The same holds for a path written in an --overlay file or in a --set value.

the folder of the file that holds it

a relative export.folder

the share/ folder of the project

a relative export.file

the folder of the same block

The <role> is the kind of data: dem, hydrography, and so on. The workspace is found in this order: [workspace] with root or data_dir, the environment variable HMP_WORKSPACE, the layout <workspace>/projects/<name>/project.toml beside a data/ folder, and last the project folder itself. This is why a file can write dem_init_path = "dem.tif" and not a full path: the file sits in the data folder of the workspace.

Profiles#

Every key has a profile: user, dev or expert. Of the 1760 keys of the registry, 1058 are user, 607 are dev and 95 are expert. The profile says who needs the key. It does not forbid anything: a file that writes a dev key, such as simulation.time.substeps_per_period, is valid. The profile decides what the reference shows by default, and what the terminal prints:

hmp config template --profile user
hmp config schema --section flow --profile dev

One case needs care. A choice can require keys of a higher profile: mode = "tabulated" of flow.param.<id>.field_vertical_profile.mode needs depths and factors, and both are tagged dev. The profile key of [workflow] is unrelated: it times a run.

Check a file#

hmp config check loads the file, follows base_config, validates the merged result and prints the path of the first error.

$ hmp config check typo.toml
Config invalid: typo.toml: Unknown TOML key(s) in [flow]: flow_regme

$ hmp config check conflict.toml
Config invalid: 1 validation error(s) in conflict.toml:
  conflict.toml:3: flow.param.K.field.homogeneous: Value error, K.value mixes conflicting units: 'm/h' and 'm/s'.

The second file wrote value = "0.36 m/h" under a parent that had unit = "m/s". The key unit was inherited, so the two units disagreed. hmp config targets <file> lists the names a calibration can move, with their value, unit and path.
