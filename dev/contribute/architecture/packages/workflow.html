Package: workflow#

The order in which a project is built and run. A file such as step4_transient.toml becomes twelve steps, from validation to export. Each step takes an immutable PipelineState, does its part and returns the next one. A Pipeline chains the steps, records them in a journal in the project catalog, and can resume a run from the artifacts of the steps already done. The Project facade and every workflow launcher (simulation, calibration, comparison, site selection) call these steps, so one file always drives one lifecycle. This file is the map of the package: what each part answers, the import rules, the twelve steps, and where to add what.

Parts#

answers

the twelve canonical steps, one module per concern; each exposes step_* functions and a *Step class that adapts them to the Step protocol

run_catalog.py

the writable catalog of a run, opened for the span of one caller

Import rules#

tests/unit/architecture/layer_matrix.yaml gives workflow every layer below it, itself included. Today it imports core, config, physics, data, spatial, simulation, solver, calibration, results, display, analysis and reporting. Rules:

  1. No lower layer imports workflow. Only project, cli and the package root do. A lower layer that needs a workflow function receives it through a provider: calibration reaches the trial pipeline through calibration/runners/contracts.py, filled by register_default_trial_pipeline_provider.

  2. Inside the package, steps/ imports internals/, runner.py, orchestrator.py, launcher_protocol.py and run_catalog.py; runner.py imports dag, internals, parallel and tracking. internals/ and tracking/ import no step.

  3. A step’s reads and writes are exact. tests/unit/architecture/test_step_payload_keys.py derives both from the source of the step and fails when a declaration and the code disagree in either direction. test_workflow_context_members_have_a_reader.py requires every member of WorkflowContext to have a reader.

  4. Step is a runtime-checkable Protocol of name and run. reads, writes and config_sections are class variables of _TypedStep, and earliest_affected_step reads config_sections.

How a run goes through it#

  1. Build. standard_steps() makes the twelve steps. Pipeline(steps, workspace=...) builds the graph from depends_on().

  2. Run. Pipeline.run(state, resume_from=..., parallel=...) takes an initial PipelineState. Each step is state.advance(...) over the shared payload; the dominant member is ctx, the WorkflowContext. A cohort of several steps would go through a thread pool; the twelve steps give only single-step cohorts.

  3. Journal. Each step is recorded in the workflow_steps table of the project catalog with the hash of its artifacts, and a heartbeat marks a live run. ResolvedRunManifest records the step blueprint and the config digest under .hmp/checkpoints/<run_id>/resolved_manifest.json.

  4. Resume. A step that writes durable artifacts implements artifacts(state_out) and rebuild_state(...). At resume the runner rebuilds the state of a completed step from disk and does not run it again. There is no pickle layer and no checkpoint store: resume reads artifacts. See docs/source/contribute/architecture/pipeline_resume.rst.

  5. Window. ProjectRunner.run bounds the step window with from_step and until_step. A calibration trial skips the shared steps: it asks earliest_affected_step for the first step an override reaches, from the config_sections of the steps.

Where to add what#

to add

where

a step

a module in steps/ with its step_* function and *Step class, exported by steps/__init__.py, placed in standard_steps(), with depends_on, reads, writes and config_sections

a persistent step

artifacts and rebuild_state on the step, so a resume can skip it

a derived field

a row of VIRTUAL_FIELD_ROWS in results/derive/virtual_fields.py: it is rebuilt on read, never written by a step

a way to bind loaded data

a function in steps/data.py calling the binder of physics or spatial

a workflow mode

a name in KNOWN_WORKFLOWS (dispatch.py) and its adapter in project/dispatch/workflow.py; see project/README.md

a standalone launcher

a class in pipelines/ on the steps it needs

a launcher backend

a class that satisfies Launcher in launcher_protocol.py

a key of the shared payload

the key in the reads and writes of the steps that touch it, in the same commit
