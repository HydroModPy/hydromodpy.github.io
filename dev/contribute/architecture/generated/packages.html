Packages#

One row per sub-package of hydromodpy. The summary is the first paragraph of its README.md, the map of the package.

Layer

Modules

Summary

analysis

yes

68

21 318

Workflows that work across runs. analysis compares simulations that share a case, runs a matrix of controlled variants of a method, and publishes selected figures of a run to a gallery folder. It runs on finished runs and on child TOML files it writes itself; it implements no physics. The HTML pages built on top of a comparison live in hydromodpy/reporting. This file is the map of the package: its parts, how a workflow reaches it, the import rules and where to add what.

calibration

yes

107

36 411

Fitting model parameters to observations. A [calibration] table names the parameters to vary, the outputs to compare, the criterion that scores them and the search method. The package turns that table into a search: an optimizer proposes parameter values, one trial runs the model with them, the outputs are scored against the observations, and the session is written to disk as it goes. This file is the map of the package: what each part answers, the import rules, how a calibration flows, and where to add what.

catalog

yes

2

93

A read-only view over the input cache of a workspace. The package is one class, InputsNamespace, which answers “what did this workspace download or convert, and for which extent?” from <workspace>/data/cache.duckdb. It is exposed as hmp.catalog. This file is the map of the package, and of the two other DuckDB scopes people confuse it with.

cli

yes

93

14 149

The command line: the hmp and hydromodpy entry points. It parses arguments, calls the code that does the work, formats the output and turns an exception into a typed exit code. It holds no scientific logic. This file is the map of the package: its parts, the verbs, the contract of a verb, the boundary with the rest of the code, and where to add what.

config

yes

7

3 471

The root of the configuration. HydroModPyConfig is the one Pydantic model that aggregates every section of a project TOML. Anything a user can write in a project file must load through it and round-trip. This file is the map of the package: what is here, which section is owned by which package, how a TOML becomes a validated object, and where to add what.

core

yes

120

22 087

The kernel leaf. Every other layer may import core, and core imports no sibling layer, not even under TYPE_CHECKING. It holds what several layers need and none should own: the base of every config model, units, workspace and path rules, runtime state, I/O primitives, the typed exceptions, and a few numerical kernels (efficiency metrics, descent on a mesh) that two layers must compute the same way. This file is the map of the package: what each part answers, the import rule, and where to add what.

data

yes

210

28 393

Everything a run reads from outside: provider APIs, user files, their cache and the typed records handed to the layers above. This file is the map of the package: what each subpackage answers, the import rules, the template of a variable, how data flows, and where to add what.

display

yes

119

28 616

display draws. It takes a run that is already computed (hydromodpy.results.run.Run) or data that is already loaded, and writes PNG figures and HTML pages. It never runs a solver, never reads a raw solver file and never writes into the storage of a run (Zarr, Parquet, DuckDB). Everything a figure reads from a run goes through the public API of results. One reader is left over: the catchment report context (catchment_report/context.py) still queries three Parquet tables of the run directory with DuckDB (runtime, provenance counts, network segment counts).

examples

yes

5

910

What hmp example stands on: the catalog of shipped examples, the cache their files are fetched into, and the generator that writes the catalog from a checkout. It is a leaf above core. The CLI and the Python API (example_list, example_show and example_add of hydromodpy/_api.py) import it. This file is the map of the package.

physics

yes

83

15 389

The physical processes of a model, written without any solver. A [flow] table says which parameters, initial heads, boundaries and sinks and sources the groundwater has. A [transport] table holds the tracking and transport settings. This package turns those tables into typed config models, and the config models into runtime objects (Flow, Transport) that the solver adapters read. It also holds the rules that bring loaded data into a Flow (recharge, ETP, lakes, stream reaches, barriers), and the daily soil reservoir that turns precipitation and ETP into recharge. This file is the map of the package: what each part answers, the import rules, how a Flow is built, and where to add what.

project

yes

13

2 846

A project driven from Python: one object, Project, that holds a validated configuration, builds the model once, and runs it as often as asked. The same package carries the adapters that bind a workflow name (simulation, calibration, …) to a Project, which hmp run and hmp.run use. Project is not an execution engine. It calls the workflow layer, so the interactive route and the TOML route share the same steps. This file is the map of the package: what each module answers, the import rules, how a run goes through it, and where to add what.

reporting

yes

22

7 076

Standalone HTML pages that put several results side by side. A calibration session becomes one page with its convergence figures and its best fit. A comparison of simulations becomes a browsable report. A site selection becomes a review page. Figures come from display, derived series from analysis, data from results; this package composes them and writes the page. This file is the map of the package: what each part answers, the import rules, who calls it, and where to add what.

results

yes

110

32 124

What a run leaves on disk, and how it is read back. Each run owns a directory of Zarr arrays and Parquet tables, sealed by a manifest. A DuckDB index lists the runs so they can be found, ranked and compared. Catalog writes and reads the project; Run is one finished simulation. Exporters turn a run into the formats others use. This file is the map of the package: what each part answers, the import rules, how a run is written and read, and where to add what.

schema

yes

23

4 796

The contracts that something outside the Python code relies on. Two kinds. The first is for a front end: the JSON Schema of the whole configuration and a validator for one field at a time, so a form can check a value without loading a project. The second is for an orchestrator: the job directory a capability is invoked through as an external process, the declaration of each capability, its generated description, and the licence of each data source. This file is the map of the package: what each part answers, the import rules, how a job directory is written, and where to add what.

simulation

yes

21

4 372

From the [simulation] table to a solved run and the outputs read back from it. The table lists processes (a mesh, a flow, a transport) and the solvers each one runs. This package turns that list into an ordered plan, walks the plan one run at a time, hands each run to the adapter of its solver, and afterwards reads the solver files into the results store. It knows no solver: the solver registry is reached through a provider that the root bootstrap wires. This file is the map of the package: what each part answers, the import rules, how a plan becomes a run and then results, and where to add what.

solver

yes

236

51 027

The numerical backends. A [solver] table picks the flow backend, and a [[simulation.process]] entry names the solvers each process runs. This package holds the adapters that turn a built Flow or Transport into a backend run, the extractors that read the backend’s files into the results store, and the registry that pairs a (process_type, solver_name) key with each. Three flow backends ship: MODFLOW 6, MODFLOW-NWT and Boussinesq, plus the transport tools that go with them. This file is the map of the package: what each part answers, the import rules, how a run reaches a backend, and where to add what.

spatial

yes

330

70 051

Where the model is in space. From a DEM and an outlet to a catchment, its river network and the ground of the model; from the ground and a depth model to the domain; from the domain to a mesh; and the fields that carry a value per zone, per cell or per depth onto that mesh. Sites that fit a study are selected here too. The package knows no solver and no data provider: the geology source is registered at start-up, and a mesh leaves as a HydroMesh that each solver converts. This file is the map of the package: what each part answers, the import rules, how a catchment becomes a mesh, and where to add what. field/, geographic/, mesh/ and site_selection/ each have a note of their own.

workflow

yes

46

11 104

The order in which a project is built and run. A file such as step4_transient.toml becomes twelve steps, from validation to export. Each step takes an immutable PipelineState, does its part and returns the next one. A Pipeline chains the steps, records them in a journal in the project catalog, and can resume a run from the artifacts of the steps already done. The Project facade and every workflow launcher (simulation, calibration, comparison, site selection) call these steps, so one file always drives one lifecycle. This file is the map of the package: what each part answers, the import rules, the twelve steps, and where to add what.
